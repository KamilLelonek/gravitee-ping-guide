Gravitee API Management on local Kubernetes

In one paragraph

make up builds a one-node Kubernetes cluster in Docker with k3d and installs Gravitee API Management Community Edition: the gateway, the Management API and the Console, with MongoDB as the database. The API itself is a Kubernetes resource that the Gravitee operator publishes. An operator is a small controller program that runs as a pod in the cluster. It reads one kind of Kubernetes object and makes Gravitee's own state match it. So everything is code, and re-running changes nothing. A small nginx backend answers pong, and only the gateway may reach it. TLS comes from cert-manager with a local CA and renews by itself. make test proves the README's claims, and make down removes everything.

01 · Where everything runs

One cluster inside Docker

Everything runs in one k3s node inside Docker. Traefik owns port 443 and sends each path to the right service. The gateway is the only part on the request path, and it reads its APIs from MongoDB, not from the Management API.

Key points

  • The gateway never calls the Management API to serve traffic.
  • If the Management API stops, /ping still works.
  • The Console is only a web page. The browser loads it from /console, then calls the Management API through /management.
  • Two gateway pods and a PodDisruptionBudget keep /ping up during a rolling update.

Why Traefik

  • It ships with k3s, so there is nothing extra to install.
  • ingress-nginx is archived.
  • One entrypoint serves the Console and the gateway.

Numbers

  • 1.6 CPU and 2.5 GB requested.
  • About 3.9 GB used when idle.
  • About 1.9 GB of images.

02 · One request

GET /ping, step by step

Traefik decrypts TLS and passes plain HTTP to a gateway pod. The gateway finds the API by its path, checks the flow, and calls pong. A POST matches no flow, and matchRequired: true makes the gateway answer 404.

Key points

  • Anyone can call /ping. The caller sends no API key or password.
  • The flow is a filter that only matches GET.
  • The body is exactly pong, with no newline, because nginx uses return 200 'pong'.

Edge cases

  • /ping/extra reaches pong, which answers its own 404.
  • /pingx matches no API, so the gateway answers 404.
  • POST /ping gets 404 from the gateway.

03 · How the API gets there

From YAML to the gateway

The API is a Kubernetes object, so it lives in git like everything else. The operator turns it into a REST call to the Management API, which saves it in MongoDB. Every gateway polls MongoDB and loads the new API within seconds.

Key points

  • syncFrom: MANAGEMENT puts the API in MongoDB, so it also shows in the Console.
  • The operator writes processingStatus: Completed, and up.sh waits for it.
  • If it fails, up.sh prints the operator's own error message.

If MongoDB stops

  • Gateways keep serving the APIs they already loaded.
  • New or changed APIs do not arrive.
  • Sync errors show in the gateway logs.

04 · One command up

What make up does, in order

Every step waits for the one before it. Each step either installs with helm upgrade --install, applies a file, or creates a secret only if it is missing. That is what makes the script safe to run twice.

Key points

  • make test runs make up again and checks that no pod restarted.
  • Every kubectl and helm call names --context k3d-gravitee, so no other cluster is touched.
  • Helm keeps its cache and config in .helm/ inside the project.

Two waits that matter

  • The operator creates its CRDs only when it starts, so step 6 waits for them.
  • The operator's webhook can refuse calls for a few seconds after start. Step 8 retries only that error.

05 · Security

Who may talk to whom

Port 443 listens only on 127.0.0.1, so other machines cannot reach it. Inside the cluster, NetworkPolicies decide who may connect. make test proves it with two probe pods: one has the gateway labels, one does not.

Key points

  • Only the gateway may call pong, so nobody can bypass it.
  • Only Gravitee pods may reach MongoDB on 27017.
  • The MongoDB password and the token key are generated on the first run and never touch git.

Also hardened

  • Every pod runs as non-root with all capabilities dropped.
  • The chart's sample users are removed.
  • The chart's public token signing key is replaced with a random one.

Honest gap

  • Console login is still admin/admin, the chart default.
  • It is item 1 on the production list.

06 · Before production

Today versus production

The demo uses production settings where they fit on one laptop. These four changes and two additions are what a real environment still needs. Each number in the CHANGES list matches the same number on a box or a line in the right panel.

First week in production

  • Replace the default logins and put the Console behind SSO.
  • Run MongoDB as a replica set with backups.
  • Alert on the 5xx ratio and on sync errors.

Why not now

  • Changing the admin password needs a bcrypt hash and more secret wiring, which did not fit the 3 to 4 hour box.
  • Elasticsearch is the heaviest part and was optional in the brief.

What Gravitee is

What an API is

An API (Application Programming Interface) is a door into a program that another program can call. Here it is an HTTP address. You send GET https://localhost/ping and get back the text pong.

What an API gateway is

Picture a hotel reception desk. Guests never walk straight into the kitchen. They ask the reception, and the reception checks who they are, decides if they are allowed, and passes the request on.

An API gateway is that reception desk for APIs. Every request goes through it first. It can:

  • check an API key or a login token (security),
  • limit how many calls one client makes per minute (rate limiting),
  • change headers or the body on the way in or out,
  • count requests and measure time (analytics, metrics),
  • send the request to the right backend (routing).

The backend (here pong) then only has to do its own job.

What API management (APIM) is

A gateway alone is just the reception desk. API management adds the office behind it: a place to design APIs, publish them, give developers keys, and see statistics. Gravitee APIM (API Management) is an open-source product that does all of this.

The parts of Gravitee APIM

The single most important idea: the gateway reads its APIs from MongoDB, not from the Management API. So if the Management API is down, traffic still flows.

admin -> Console -> Management API -> MongoDB <- gateway (reads every few seconds)
                                                     ^
client  ---------------------------------------------+ (real traffic)

Community Edition (CE) vs Enterprise Edition (EE)

CE is free and open source. EE needs a paid license key and adds extra features. The brief asks for CE, so no license is used.

What is missing before production

  1. Default logins admin/admin (Console) and admin/adminadmin (gateway technical API). Change them and use a secret manager like Vault.
  2. Console behind SSO, on an internal address, separate from public API traffic. The gateway technical port 18082 open only to the monitoring namespace.
  3. MongoDB replica set with backups and its own application user (today Gravitee uses the root user), or a managed service.
  4. Several nodes, anti-affinity (copies of a pod placed on different nodes), and a HorizontalPodAutoscaler (adds gateway pods when CPU use is high).
  5. Analytics (Elasticsearch), Redis for rate limiting, Prometheus + Grafana + alerts.
  6. CI that renders the charts with helm template and checks them with kubeconform (a Kubernetes schema validator), and images pinned by digest (the exact image content, not a tag that can move).
  7. Read-only root filesystem for the Gravitee containers. They write logs and temp files, so each needs small writable volumes for those folders.
  8. Real DNS name + Let's Encrypt, through cert-manager's ACME issuer (the protocol Let's Encrypt uses to check you own the name).
  9. GitOps (Flux or Argo CD: a controller in the cluster applies whatever is in git) instead of re-running a script.
  10. Credentials on the plan (an API key, or a JWT login token), and a rate-limit policy. Without them, anyone can call the API as often as they like. That is fine for /ping, but not for a real API.
  11. Scheduled, tested backups. make backup exists, but someone has to run it.
  12. Logs shipped to a central store, for example Loki. Today they stay in the pods.
  13. TLS inside the cluster. Traffic from Traefik to the gateway and from the gateway to pong is plain HTTP.

admin/admin is the chart default. It is item 1 on this list, and the stack listens only on 127.0.0.1. Changing it needs a bcrypt hash (the one-way password format Gravitee stores) and more secret wiring, which did not fit the 3 to 4 hour time box.

Monitoring

The gateway has a Prometheus endpoint on port 18082 (/_node/metrics/prometheus). Watch:

  • error ratio: http_server_requests_total{code=~"5.."} vs all requests,
  • latency: http_server_response_time_seconds (sum, count, max; no percentiles without histogram buckets),
  • load: http_server_active_requests,
  • Java memory: jvm_memory_used_bytes vs the 512 MB heap, and jvm_gc_pause_seconds,
  • pod restarts and certificate expiry.

A Prometheus Operator ServiceMonitor with basicAuth would scrape the endpoint, because the technical port asks for a login. Per-API numbers and errors such as a lost MongoDB connection are not in these metrics. They come from the analytics reporter and the gateway logs, which this setup does not ship anywhere.

Upgrading

Versions are pinned in three places: the chart versions at the top of scripts/up.sh, the image tags in values/, and the k3s image in k3d.yaml. The operator and APIM share version lines, so GKO_VERSION and APIM_VERSION move to a new minor together.

  1. Read the release notes for every version that changes.
  2. Back up MongoDB with make backup. It writes a mongodump archive to backups/.
  3. Change the versions, then run make up and make test. Charts upgrade in place. A new k3s image only applies to a new cluster, so it needs make down first.
  4. Roll back a chart with helm rollback <release> --kube-context k3d-gravitee -n <namespace>. If the new APIM version changed the database, restore the backup too.

Design questions and answers

Gravitee basics

What does the gateway do on each request here?

Finds the API by path /ping, checks the plan (no credentials needed), checks the flow (GET only), forwards to pong, returns the answer.

Why does the API need a plan if it is open?

Gravitee only serves an API that has a published plan. The plan is the rule that says how callers prove who they are. Here the plan is named Keyless: it asks for nothing, so anyone can call /ping. A real API would use a plan that asks for an API key or a token.

Management API down: what happens?

/ping keeps working. The gateway reads MongoDB, not the Management API. You just cannot change APIs until it is back.

MongoDB down?

The gateway keeps serving the APIs already in memory. New or changed APIs do not arrive. Sync errors show in the gateway logs.

Why 2 gateways but 1 Management API?

The gateway carries client traffic, the Management API does not. 2 gateways + PDB keep /ping up during a rolling update.

Does the Console talk to MongoDB?

No. The Console pod is a small web server that only hands out HTML, JavaScript and CSS. The page runs in your browser, and your browser calls https://localhost/management/.... That request goes through Traefik to the Management API, and only the Management API talks to MongoDB.

Do more gateways need to talk to each other?

No. Each one reads MongoDB on its own.

What does /ping/extra do? /pingx?

/ping/extra matches /ping and the rest is appended, so pong gets /ping/extra and returns its own 404. /pingx matches no API and the gateway returns 404.

Kubernetes and the setup

Why the operator and not a REST call?

The API becomes a Kubernetes file: versioned in git, reviewed, re-applied safely. A script must handle "already exists" and needs the admin password at runtime.

What does idempotent mean, and how did you prove it?

Running twice gives the same state. make test runs make up again and checks no pod restarted. Re-run takes about 18 s.

Each re-run adds a Helm revision. Is that really "no change"?

A new revision with the same manifests changes no pod. Measured: no restarts. GitOps would avoid the extra revisions, that is item 9.

What if my kubectl points at production?

Every command names --context k3d-gravitee. The current context is never used.

Why a PDB on a single node?

A PDB protects against planned evictions such as a rolling update or a node drain, even on one node. On a real cluster the same file spreads across nodes.

Why Traefik in front of a gateway? Is that not two proxies?

Traefik owns TLS and routing for everything in the cluster, including the Console. The gateway owns API rules. The gateway could do TLS itself, but then the Console would need a second door.

You chose Traefik over nginx, but you use nginx anyway?

They do different jobs at opposite ends of the request: curl -> Traefik (the door) -> gateway (the API rules) -> nginx (the backend). What is archived is ingress-nginx, an ingress controller. The nginx web server itself is maintained, and here it is only a 6-line backend that returns pong.

How does certificate renewal work?

cert-manager makes a new certificate 8 hours before the 24-hour one expires and updates the Secret. Traefik watches the Secret and serves the new one without a restart. Demo: delete Secret localhost-tls, cert-manager recreates it, make ping still passes.

Why not Let's Encrypt, so nobody needs --cacert?

Let's Encrypt only signs names on the public internet, and localhost is not one. It also has to check that you control the name. The HTTP check needs the machine reachable from the internet on port 80. The DNS check needs a domain you own and an API token for its DNS provider. Each reviewer runs make up on their own laptop without that token, so one command up would break. The local CA renews certificates the same way, and production only swaps the issuer for Let's Encrypt.

Could the configuration be smaller?

Yes, for a plain dev setup: one gateway, no TLS, no probes, no security settings, no resource limits. But the brief grades production-grade configuration, and each of those lines is one of its signals. Two gateways with a PodDisruptionBudget keep /ping up during an update. The HTTP readiness probe stops traffic before the Management API is ready, which the chart's port check does not. Resource limits prove the stack fits the 4 CPU / 6 GB budget. Everything else is already off: analytics, Developer Portal, SMTP, autoscaling, sample users.

How does the MongoDB password travel?

openssl rand -hex 32 piped into kubectl create secret --from-file=password=/dev/stdin, only if missing. Hex keeps the URI valid, stdin keeps it out of process lists.

Why mongo.auth.enabled: false when MongoDB has a password?

That flag only controls what the chart writes into its ConfigMap. The real URI with the password arrives from a Secret through the variable gravitee_management_mongodb_uri, so the password is never in a ConfigMap.

Why is the heap 512 MB in a 1 GiB container?

Java needs memory outside the heap too: threads, class data, network buffers. The image sets 256 MB unless GIO_MIN_MEM and GIO_MAX_MEM are set. Min equals max so the heap never resizes.

Why POSIX sh and not bash?

macOS ships bash 3.2 and Ubuntu uses dash for /bin/sh. Plain sh runs the same on both. Checked with shellcheck -s sh, tested in Ubuntu 24.04.

Why not Terraform or helmfile?

More tools to install for no gain at this size. The steps must wait for each other (the CRDs appear at runtime), and a script shows that plainly.

Edge cases

The first six were measured with curl on the running stack. The last three are checks inside scripts/up.sh.

GET /ping/ with a trailing slash?

404 from nginx. The gateway forwards /ping/ to pong, and nginx only answers the exact path /ping.

GET /ping?x=1?

200 and pong. The query string does not change which API or flow matches.

HEAD /ping or OPTIONS /ping?

404 from the gateway. The flow matches only GET, and HEAD is a separate method. A load balancer health check that sends HEAD would see 404, so it should send GET.

GET /PING?

404 from the gateway: "No context-path matches the request URI". Paths are case-sensitive.

http://localhost/ping (no TLS)?

Connection refused. Only port 443 is mapped from the host, so plain HTTP never reaches the cluster.

https://127.0.0.1/ping?

TLS error (curl exit code 60). The certificate is issued for the name localhost, not for the IP address.

Port 443 is already taken on the host?

make up stops before creating the cluster and says so. It checks with curl: exit code 7 means "connection refused", so the port is free.

Docker is not running?

make up stops in its first step with a clear message, before it changes anything.

The Management API is not reachable for a few seconds right after install?

make up retries applying the API. The operator checks every API with a dry-run call to the Management API, and that call can be refused for a moment after Helm reports the pod ready. Only this error and the operator's own webhook error are retried, 10 times, 5 s apart. Any other error stops at once.

Trade-offs and limits

You call it production-grade but it has admin/admin.

Agreed, it is the biggest gap, and it is item 1 on the production list. Everything else on the production list is in place, and the stack listens only on 127.0.0.1. With more time I would put bcrypt hashes in a Secret, or put the Console behind SSO.

There is a password in git (apim-admin-credentials).

It is the chart's public default, not a secret I made up. The operator needs it to talk to the Management API. In production it would come from Vault through External Secrets (an operator that copies secrets from a vault into Kubernetes Secrets).

What happens if two people run make up at the same time?

It is not guarded. Helm would refuse the second upgrade with "another operation is in progress". On one laptop it does not happen, and in a team it is a reason to move to GitOps.

How would you scale this to a lot of traffic?

More gateway replicas with an autoscaler on CPU, several nodes, Redis for rate-limit counters instead of MongoDB, and an asynchronous analytics reporter.

Gravitee 4.13 is out. Why are you on 4.12?

Gravitee releases the operator (GKO) in the same version lines as APIM: GKO 4.12 goes with APIM 4.12. GKO has a 4.13 branch on GitHub but no 4.13 release yet, so APIM 4.13 with GKO 4.12 would be a pair nobody tested. The stack takes the newest 4.12 patch, 4.12.25, and moves to 4.13 when GKO 4.13 ships. Patch releases only fix bugs and security issues, so they are safe to take at once.

How would you upgrade Gravitee 4.12 to 4.13?

Read the upgrade notes, run make backup (a mongodump archive in backups/), change APIM_VERSION, GKO_VERSION and the image tags in values/apim.yaml, run make up and make test on a test cluster, then production. Rollback: helm rollback plus the database backup if the schema changed.

How would you add a second API?

Copy ping-api.yaml, change name, path and target, kubectl apply. The operator publishes it, the gateways load it within seconds.

/ping returns 404. How do you debug?

  1. kubectl --context k3d-gravitee -n gravitee get apiv4definition ping - is it Completed?
  2. Gateway logs: kubectl --context k3d-gravitee -n gravitee logs deploy/apim-gateway - did it load the API?
  3. curl -v - is the 404 from Traefik (no route) or from the gateway (no API or no flow)?
  4. Call pong from inside the cluster with the gateway labels, like make test does.

Why one node, not three?

A laptop demo. The settings (replicas, PDB, NetworkPolicies) are the same as on a real cluster; only anti-affinity is missing (item 4).
